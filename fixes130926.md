### [CRÍTICO] C1. `loadData` sobrescribe cambios locales no sincronizados con nube vacía

- **Archivos**: `src/storage.js:686-695`, `src/App.jsx:380-391`
- **Problema**: `shouldPreferLocal` solo se activa si `resolvedProfileId` es falsy, por lo que en multi-workspace es código muerto y una nube vacía pisa `localStorage`. Además `App.jsx:391` marca el payload descargado como `lastSyncedPayloadRef` y nunca reenvía lo perdido.

  Snippet actual:
  ```js
  const shouldPreferLocal = !resolvedProfileId && hasAnyData(localData) && !hasAnyData(safeCloudData);
  const effectiveData = shouldPreferLocal ? localData : safeCloudData;
  ```
- **Fix propuesto**:
  1. Para perfil explícito, conservar/mergear local si `hasAnyData(localData) && !hasAnyData(safeCloudData)`.
  2. Alternativamente comparar recencia (`updatedAt`/`updated_at` máximo) antes de sobrescribir.
  3. Reenviar a la nube el estado conservado (no marcarlo como ya sincronizado en falso).
  ```js
  // src/storage.js
  const localHasData = hasAnyData(localData);
  const cloudHasData = hasAnyData(safeCloudData);
  const shouldPreferLocal =
    localHasData &&
    (!cloudHasData || localLooksNewerThanCloud(localData, safeCloudData));
  const effectiveData = shouldPreferLocal ? localData : safeCloudData;
  ```
- **Verificación**: test unitario en `tests/` que simule cloud vacío + local con datos y afirme que se conserva `local`.
- **Estado**: `[x]` implementado y verificado

### [CRÍTICO] C2. Subtasks legacy/shape inconsistente + `normalizeDataPayload` todo-o-nada borra el payload

- **Archivos**: `src/storage.js:158-160` y `273-275`; render roto en `src/components/TaskRow.jsx:47,332-339` y `src/components/KanbanView.jsx:96-97`
- **Problema**: `isValidTask` exige `{id,text,done}` pero datos históricos usan `{id,title,completed}`; `normalizeTask` no convierte; y el saneo todo-o-nada descarta TODO el dataset si una sola tarea es inválida. Igual con prioridad legacy `'urgent'`.

  Snippet actual:
  ```js
  if (!tasks.every(isValidTask)) return { tasks: [], boardNotes: [], events: [] };
  const completedSubtasks = subtasks.filter((st) => st.completed).length; // siempre 0
  ```
- **Fix propuesto**:
  1. Normalizar legacy en `normalizeTask`: `text = st.text ?? st.title`, `done = st.done ?? !!st.completed`, `id` a string.
  2. Mapear prioridad legacy: `urgent -> critical`.
  3. Cambiar `normalizeDataPayload` a saneo **por-item** (filtrar/map), nunca retornar arrays vacíos globales.
  ```js
  function normalizeSubtask(st) {
    if (!st || typeof st !== 'object') return null;
    return {
      id: String(st.id ?? uid()),
      text: String(st.text ?? st.title ?? '').trim(),
      done: Boolean(st.done ?? st.completed ?? false),
    };
  }
  ```
  ```js
  const safeTasks = (Array.isArray(raw.tasks) ? raw.tasks : [])
    .filter(isValidTask)
    .map(normalizeTask);
  ```
- **Verificación**: test con task con subtasks `{title,completed}` que afirme que se conserva y se normaliza (`text`/`done` presentes).
- **Estado**: `[x]` implementado y verificado

### [ALTO] A1. Vectorize `deleteByIds` sin namespace

- **Archivos**: `src/noteAi/pipeline.js:229-233`, `src/noteAi/adapters.js:127-130`
- **Problema**: `deleteByIds` no recibe el namespace aislado por `userId+profileId`; al borrar/regenerar vectores se pueden dejar vectores huérfanos o afectar el espacio equivocado. Se viola la regla de aislamiento Vectorize.
- **Fix propuesto**:
  1. Propagar `namespace` por la firma del adapter.
  2. Llamar con `{ namespace: await vectorNamespace(userId, profileId) }`.
  3. En full-reset (`payload` mode), encolar `delete` para las notas eliminadas.
  ```js
  await vectorStore.deleteByIds(ids, {
    namespace: await vectorNamespace(userId, profileId),
  });
  ```
- **Verificación**: test unitario de `noteAi` que verifique que `deleteByIds` recibe el namespace esperado y que full-reset encola deletes.
- **Estado**: `[x]` implementado y verificado

### [ALTO] A2. `sendBatch` sin trocear (>100)

- **Archivos**: `src/noteAi/pipeline.js:559-567`, invocado desde `worker.js:1798-1799`
- **Problema**: `sendBatch` de Cloudflare Queues admite como máximo 100 mensajes. Un workspace grande genera más y la llamada falla justo después del commit del sync.
- **Fix propuesto**: trocear en lotes de ≤100 antes de `sendBatch`.
  ```js
  const QUEUE_BATCH_LIMIT = 100;
  for (let i = 0; i < messages.length; i += QUEUE_BATCH_LIMIT) {
    await env.NOTES_AI_QUEUE.sendBatch(
      messages.slice(i, i + QUEUE_BATCH_LIMIT)
    );
  }
  ```
- **Verificación**: test unitario que genere >100 mensajes y afirme que `sendBatch` se llama en N lotes ≤100.
- **Estado**: `[x]` implementado y verificado

### [ALTO] A3. Sync devuelve 500 tras commit si falla el encolado

- **Archivos**: `src/worker.js:1798-1799`
- **Problema**: si el enqueue de Note AI falla después de confirmar el batch en D1, el worker propaga el error y responde 500 aunque los datos ya estén comprometidos; el cliente reintenta creyendo que no se guardó.
- **Fix propuesto**: envolver `enqueueNoteAiJobs` en try/catch **best-effort**: loguear (con hash, nunca userId en claro) y continuar devolviendo éxito.
  ```js
  try {
    await enqueueNoteAiJobs(env, { userId, profileId, notes });
  } catch (err) {
    console.error('note-ai enqueue failed', { profile: shortHashForLog(profileId), error: String(err) });
  }
  ```
- **Verificación**: test/ajuste que simule fallo de `sendBatch` y afirme respuesta 200 tras commit.
- **Estado**: `[x]` implementado y verificado

### [ALTO] A4. `del()` lee resultado mutado dentro del updater

- **Archivos**: `src/App.jsx:1088-1135`
- **Problema**: `del()` calcula bloqueo de parent / snapshot / undo leyendo estado mutado dentro del updater de `setTasks`, lo que produce resultados no deterministas (doble invocación en StrictMode, side effects).
- **Fix propuesto**: calcular bloqueo y snapshot **fuera** del updater usando el `tasks` del render (mismo patrón que `TaskTrashDropZone` / `countOpenChildTasks`) y dejar `setTasks` puro.
  ```js
  const hasOpenChildren = tasks.some(
    (t) => t.parentId === taskId && !isTerminalStatus(t.status)
  );
  if (hasOpenChildren) return showParentBlockedMessage();
  const snapshot = tasks;
  setTasks((prev) => prev.filter((t) => t.id !== taskId));
  pushUndoTransaction({ description: 'Tarea eliminada', rollbackFn: () => setTasks(snapshot) });
  ```
- **Verificación**: test/validación manual de borrado con hijos abiertos y undo; sin toasts dentro del updater.
- **Estado**: `[x]` implementado y verificado

### [ALTO] A5. `linkStandaloneTaskAsChild` retorna valor calculado dentro del updater

- **Archivos**: `src/App.jsx:806-843`, `src/components/KanbanView.jsx:652-661`
- **Problema**: la función valida y muta dentro del updater y devuelve un booleano dependiente de ese cálculo; el consumidor (`KanbanView`) recibe un retorno no fiable.
- **Fix propuesto**: validar `canLinkAsChild` de forma **pura** con el `tasks` actual antes de mutar y devolver el booleano sin depender del updater.

  ```js
  const canLink = canLinkAsChild(tasks, sourceId, targetId);
  if (!canLink) return false;
  setTasks((prev) => applyLink(prev, sourceId, targetId));
  return true;
  ```
- **Verificación**: test de cases circular/self/inválido que afirme retorno `false` sin mutación.
- **Estado**: `[x]` implementado y verificado

### [ALTO] A6. Cascada padre→hijo nunca aplicada

- **Archivos**: `src/taskStatusCascade.js:13` (nunca importada), `src/App.jsx:674-706`
- **Problema**: `applyStatusWithChildCascade` no se importa en `App.jsx`, por lo que al mover un padre a `blocked`/`paused`/`done` los hijos no se propagan; la regla documentada de cascada es letra muerta.
- **Fix propuesto**: invocar `applyStatusWithChildCascade` en `commitStatusChange` / `handleStatusCommentConfirm`, con recursión real sobre dependencias.
  ```js
  import { applyStatusWithChildCascade } from './taskStatusCascade';
  // dentro del commit
  const next = shouldCascadeStatusToChildren(newStatus)
    ? applyStatusWithChildCascade(tasks, taskId, newStatus)
    : applyStatus(tasks, taskId, newStatus);
  setTasks(next);
  ```
- **Verificación**: test unitario de cascada padre→hijo recursiva (blocked/paused/done) y de que el cobro de `completedAt` es correcto.
- **Estado**: `[x]` implementado y verificado

### [ALTO] A7. `fmtDate` crashea con fechas malformadas

- **Archivos**: `src/utils.jsx:21-25`, `src/storage.js:144`
- **Problema**: `fmtDate` indexa `MONTHS[m-1]` sin validar; una fecha malformada produce `undefined.slice` y rompe el render.
- **Fix propuesto**:
  1. Validar formato `YYYY-MM-DD` en `isValidTask`/`isValidEvent`.
  2. Hacer `fmtDate` defensivo:
  ```js
  const month = MONTHS[m - 1]?.slice(0, 3) ?? '';
  if (!month) return '';
  ```
- **Verificación**: test unitario con `date: '2026-13-99'` y `'no-date'` que afirme retorno `''` sin excepción.
- **Estado**: `[x]` implementado y verificado
